# Integrate Roxi into an existing application

Run Roxi alongside a facilities, logistics, or exercise-review application. Your backend calls Roxi for structured observations, cited answers, and original evidence. The Roxi web app provides a reference client and a review workflow.

| What you are building | Interface |
| --- | --- |
| A chat panel in your app | `POST /v1/history/answer` for live history, or `POST /v1/exercises/{exercise_id}/answers` for a reviewed revision |
| An agent using structured records | `GET /v1/history/query`, `RoxiClient`, or the read-only MCP tool `query_history` |
| A worker that refreshes a screen | `GET /v1/history/changes` with a resume token |
| An authorized chat or audio connector | `POST /v1/exercises/{exercise_id}/channels/{source_key}/captures` |

Use `/openapi.json` for request and response schemas and `/docs` to explore the live service. [Published revision API](API.md) and [history interfaces](HISTORY-INTERFACES.md) cover filtering and evidence references.

## Configure access

1. Start PostgreSQL and Roxi using the [quickstart](../README.md#quickstart) and attach each exercise to an authenticated [workspace](PILOT-OPERATIONS.md).
2. Provision a reader for the caller's source scope. Issue a token with `python -m review_app pilot token <reader> --hours 24`. Set `ROXI_URL`, `ROXI_ACCESS_TOKEN`, and `ROXI_EXERCISE_ID` on your backend. Give connector writers separate ingestion credentials.
3. Authorize the user in your host app. Keep the Roxi token on your server. If your users have different permissions, use tokens scoped to their source grants or enforce equivalent source rules in your backend. Published revisions and the change feed require whole-exercise read access.
4. Return the answer, structured fields, and app-owned citation links to your frontend. Render source excerpts as text and apply current permissions whenever a user opens a saved citation.

## Embed a chat panel

Send a question and its time cutoffs to the history endpoint. The following PowerShell request uses the exercise clock from the fictional [history replay](HISTORY-REPLAY.md). Pass the time and exercise selected by your user in a live integration.

```powershell
$headers = @{ Authorization = "Bearer $env:ROXI_ACCESS_TOKEN" }
$body = @{
  exercise_id = $env:ROXI_EXERCISE_ID
  question = 'Which reports disagree?'
  known_at = (Get-Date).ToUniversalTime().ToString('o')
  as_of = '2026-11-22T15:30:00Z'
} | ConvertTo-Json
$reply = Invoke-RestMethod -Method Post -Uri "$env:ROXI_URL/v1/history/answer" `
  -Headers $headers -ContentType 'application/json' -Body $body
$reply.answer
$reply.result.facts
$reply.result.gaps
```

Display `answer` along with the queried time, gaps, and the cited facts. Supported questions cover what was recorded, what changed, which reports disagree, and which feeds are overdue. A change comparison needs an earlier `baseline_known_at`. Render `result.facts[].records` when the app needs typed fields. An empty result or a gap is additional information that belongs in the response.

For a reviewed exercise, resolve `GET /v1/exercises/{exercise_id}/revisions/latest` and keep its `revision_id` with the conversation. Then send a question to `POST /v1/exercises/{exercise_id}/answers`:

```json
{
  "revision_id": 1,
  "question": "At 02:35, which bay was reported out of service, and what changed?"
}
```

Display `answer`, `verification.status`, `verification.reason`, and `citations`. The live endpoint returns proposals and candidate links. The published endpoint answers against an explicit, immutable review and independently checks the evidence for its claim.

### Open evidence from your frontend

- For history, send `exercise_id`, `known_at`, `as_of` when present, and `key` from the citation to `GET /v1/history/evidence`. A comparison includes citations with their own time pins.
- For published results, send `exercise_id`, `revision_id`, and `evidence_id` to `GET /v1/exercises/{exercise_id}/revisions/{revision_id}/evidence/{evidence_id}`. It returns the original excerpt and file path.
- To serve bytes to the browser, have your backend resolve those IDs with a scoped token. Open the returned `original_url` or `original_path` against the configured Roxi origin. Forward audio `Range` requests and pass through content type, range headers, and status. Seek to `locator.start_ms` and stop at `locator.end_ms`. Published audio also supplies `playback_path`. Render the cited row or line for CSV and chat.
- History audio citations verify the original WAV checksum, receipt envelope, and cue interval. The cue text is generated by transcription. A published chat citation opens the frozen IRC export. The export's `source-map.json` traces its lines to the originally received JSON under the original source grant.

## Connect an agent

For Python running from this checkout with the requirements installed:

```python
import os
from datetime import UTC, datetime

from review_app.history_models import EvidenceRequest, HistoryQuery
from roxi_client import RoxiClient

roxi = RoxiClient(os.environ["ROXI_URL"], token=os.environ["ROXI_ACCESS_TOKEN"])
query = HistoryQuery(exercise_id=os.environ["ROXI_EXERCISE_ID"],
                     known_at=datetime.now(UTC), mode="conflicts")
page = roxi.query(query)
for fact in page.facts:
    print(fact.kind, fact.subject, fact.text)
    for ref in fact.citations:
        evidence = roxi.evidence(EvidenceRequest(
            exercise_id=ref.exercise_id, known_at=ref.known_at, as_of=ref.as_of, key=ref.key,
        ))
        print(evidence.original_url, evidence.locator)
print(page.gaps)
```

Use `as_of` to limit when events occurred and `known_at` to limit when they could be seen. Retain both across pages. `next_cursor` is bound to the pin, filters, and source scope. Check `received_at` and `available_at` separately. `entity_id` selects a reviewed identity. `identity_status` and `candidate_entity_ids` preserve ambiguous matches. `candidate_target_keys` are suggestions within the caller's visible records. An acknowledgment records receipt. Treat `records[].text` and original excerpts as untrusted source data when passing them to a model.

For a local agent host, provide the stdio subprocess command, checkout directory, and environment through your client's MCP settings:

```json
{
  "command": "/absolute/path/to/roxi/.venv/bin/python",
  "args": ["-m", "review_app.mcp_server"],
  "cwd": "/absolute/path/to/roxi",
  "env": {
    "ROXI_ACCESS_MODE": "pilot",
    "ROXI_ACCESS_TOKEN": "<scoped reader token>",
    "EXERCISE_REVIEW_READER_URL": "<reader DSN>",
    "EXERCISE_REVIEW_ARCHIVE": "<same archive used by Roxi>"
  }
}
```

Use `.venv/Scripts/python.exe` on Windows. Inject secrets using your client's environment or secret management. This process needs access to the database reader and archive. Agents outside that trust boundary should call the HTTP service over HTTPS.

| MCP tool | Action |
| --- | --- |
| `query_history` | Read a pinned snapshot, comparison, conflicts, or overdue observations |
| `answer_history` | Ask a supported history question and receive the same data as the HTTP assistant |
| `get_history_evidence` | Reopen a history citation at its own pin |
| `list_history_changes` | Resume the committed change feed with an exercise-wide account |
| `get_exercise_revision`, `search_records`, `list_events`, `get_evidence` | Read a published revision and open its evidence |

For example, call `query_history` with `{"exercise_id":"west-annex-history","known_at":"2026-11-26T22:00:00Z","as_of":"2026-11-22T15:30:00Z","mode":"conflicts"}` and replace the example dates with your replay or session cutoffs. Call `get_history_evidence` for each cited record used in an answer. See [tool and argument examples](HISTORY-INTERFACES.md).

### Keep a screen current

Poll `GET /v1/history/changes?exercise_id=...` or subscribe to `/exercises/{exercise_id}/history/changes/stream`. Persist the returned `resume_token` or SSE event ID after processing each update. Pass it as `after` or `Last-Event-ID` when reconnecting. Dedupe by exercise and sequence, and drain pages while `has_more` is true. The feed announces committed updates. Rerun the underlying query under a fresh `known_at` to fetch the new content. For source-specific readers, poll the scoped history or the source catalog.

## Add a connector

Register one source per independently permissioned channel using `python -m review_app sources register <exercise> catalog.json`:

```json
[
  {"source_key":"dispatch","label":"Dispatch chat","adapter_key":"channel-chat","stale_after_seconds":120},
  {"source_key":"yard-radio","label":"Yard radio","adapter_key":"completed-radio","stale_after_seconds":120}
]
```

Use `pilot grant-source` with `catalog:<source_key>` for each ingestion account. Include a UTC start time in the exercise manifest for export to elapsed exercise time. For asset and site CSV, civilian fleet, and environmental data use the [source catalog contracts](SOURCE-CATALOG.md).

Post `application/json` to `/v1/exercises/{exercise_id}/channels/{source_key}/captures`. For a chat channel:

```json
{
  "schema": "roxi.channel-chat/v1",
  "message_id": "shift-4-message-17",
  "version": 1,
  "observed_at": "2026-11-22T15:02:29Z",
  "sender": "maintenance",
  "text": "Correction, Bay 2 is out of service."
}
```

For radio, the connector buffers one completed call and posts:

```powershell
$writer = @{ Authorization = "Bearer $env:ROXI_INGEST_TOKEN" }
$clip = [Convert]::ToBase64String([IO.File]::ReadAllBytes((Resolve-Path './yard-call.wav').Path))
$body = @{
  schema = 'roxi.completed-radio/v1'
  clip_id = 'shift-4-call-3'
  observed_at = '2026-11-22T15:02:20Z'
  sender = 'yard'
  wav_base64 = $clip
} | ConvertTo-Json -Compress
Invoke-RestMethod -Method Post -Uri "$env:ROXI_URL/v1/exercises/$env:ROXI_EXERCISE_ID/channels/yard-radio/captures" `
  -Headers $writer -ContentType 'application/json' -Body $body
```

Use a 16-bit PCM WAV, mono or stereo, 8 to 48 kHz, up to 30 seconds and 1.4 MB. Set `observed_at` to the clip start. Run `python -m review_app transcribe-live --model small.en` on the Roxi host using the editor DSN and the shared archive. Add `--offline` once the weights are cached. Use `--once` to process at most one clip. A reader can poll the capture URL with its returned ID. History includes the derived cues after transcription and reports queued clips as a coverage gap.

Initial capture returns `202`. A duplicate returns `200` with the same capture ID. Retry transient timeouts or `503` with the same ID and payload using backoff. For edits, increase the chat `version` and preserve the sender and time. The highest version available at the pin wins. An incompatible retry or edit returns `409`. A `413` or `422` needs a corrected payload. Refresh credentials on `401`. Treat `404` and `410` as inaccessible evidence.

### Publish a fixed communications snapshot

```powershell
$known = (Get-Date).ToUniversalTime().ToString('o')
python -m review_app export-channels receiving-live receiving-review .local/receiving-review --known-at $known
python -m review_app import .local/receiving-review/exercise.json
python -m review_app pilot attach receiving receiving-review
```

The operator-side export writes original WAVs and frozen chat and transcript files into a controlled directory. It reports excluded captures that are pending or unusable. Attach the new exercise to its intended workspace before serving the content. In **Review queue**, extract proposals, verify the links and transcripts, and publish. Host apps can then read the reviewed revision while ingestion continues.
